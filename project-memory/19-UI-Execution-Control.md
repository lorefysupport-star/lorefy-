# حالة خطة الواجهات وترتيب العمل

## قرار التصحيح

بعد اعتراض المستخدم على تكرار الجولات، هذه الصفحة هي مرجع **ترتيب التنفيذ
والحالة الحالية**. السجلات السابقة أدلة تاريخية، وليست قائمة مهام تتكرر تلقائيًا.
كانت جولة ترتيب الخطة تنظيمية فقط؛ تنفيذF08 اللاحق موثق أدناه. لا GitHub أو
بيلد أو كتابة خدمة في أي من الجولتين.

- الخطة الأصلية تحتوي18 ملاحظة و27 قسمًا و80 مكونًا؛ جدولها القديم يجمع98
  صفًا، وكلها ما زالت تحمل Planned - not implemented. هذه حالة لقطة ما قبل
  التنفيذ، وليست الحالة الحالية ولا دليلًا أن كل الإصلاحات ضاعت.
- الدفعات13 إلى22، وعددها10، كلها أجزاء من **F07: اتساق تحميل الصور**.
  تسجل هنا كمهمة واحدة جزئية، لا عشر مشكلات منتج مستقلة ولا عشر صفحات مكتملة.
- لا نسبة إنجاز للتطبيق من عدد الاختبارات أو الدفعات. عند مراجعة التنظيم كان
  آخر سجل2950؛ بعد تنفيذF08 أصبح2963/2963. هذا لا يعني اكتمال التطبيق.
- أدلة المتصفح السابقة محلية وبعينات محددة. لا تغلق فحص iPhone أو الخدمات
  أو الحسابين الحقيقيين، ولا تمثل اعتماد كل الخانات في27 قسمًا.

## المهمة السابقة: F08، نتائج البحث والطبعات

نفذت في [[sessions/2026-10-29-Search-Edition-Groups]]: مجموعة محافظة، زر طبعات
مستقل، نافذة ببيانات الطبعة، حفظ البحث والفلاتر والتركيز ومعرّف الاختيار.
التحقق2963 اختبار مصدر و99 حالة متصفح مضبوطة. لا كتابة حسابات أو خادم أو بيلد.
السجلات الناقصة لا تجمع بالتخمين؛ القبول الحي للمصادر والجهاز ما زال منفصلًا.

**المشكلة المحددة:** البحث يعرض كل طبعة مستقلة كبطاقة؛ المطلوب مجموعة عمل
واضحة تفتح اختيار الطبعة، لا حذف النتائج أو دمج معرّفاتها. التنظيم الحالي
للكتالوج لا يساوي هذه الواجهة، ويجب الحفاظ عليه.

### ما تحقّق من المصدر قبل تنفيذ29 أكتوبر

- `modules/lorefy-explore-studio.js`، الدالة `rankSearchResults` ترتب النتائج
  وتعيد السجلات نفسها؛ `searchBody` يرسم كل سجل بـitem. لا مجموعة طبعات في
  هذا المسار. تجربة Node محلية لطبعتين صريحتين أعادت المعرفين؛ ليست فحص متصفح.
- `modules/lorefy-catalog-identity.js`، الدالة `sameWork` تحافظ عمدًا على
  المعرفات الصريحة المختلفة للطبعات والأعداد. هذا **حاجز صحة يجب حفظه**، وليس
  عطلًا ينبغي إزالته كي تقل النتائج.
- لا تشخّص فقدان عمل أو اختلاف رواية/اقتباس أو مجلد/عدد كطبعات قابلة للدمج
  لمجرد تشابه العنوان. الحالات الغامضة تبقى مستقلة.

### النطاق وشروط التسليم

1. البدء باختبار فاشل وتجربة UI معزولة لطبعتين من العمل نفسه. نحدد عقد
   الربط الصريح المتاح قبل اختيار الخوارزمية؛ لا نفترض وجود معرّف عائلة موحد.
2. طبقة عرض فقط: مجموعة للعمل مع عدد الطبعات وإمكانية فتح كل طبعة بالمعرف
   الأصلي. البيانات المحفوظة والأغلفة والتقييمات والتقدم لا تُرحّل أو تُدمج.
3. الاختبارات تفصل العمل/الطبعة/المجلد/العدد/الاقتباس، وتشمل عنوانًا عربيًا
   ولاتينيًا وعنوانًا مشتركًا لمؤلفين مختلفين؛ التجميع الملتبس يُرفض.
4. وصول مصدر متأخر لا يسرق التركيز أو يقفز بالتمرير أو يغيّر الطبعة المختارة.
   الرجوع من اختيار الطبعة يحفظ البحث والفلاتر.
5. قبول محلي AR/EN و320/390/768 بصور نتيجة فعلية. لا إعادة تصميم الرئيسية
   أو المكتبة أو البروفايل، ولا تغيير API أو كتابة Supabase أو بناء أو رفع.
6. ينتهي العمل بتسليم هذه الرحلة كاملة. لا تقسمها إلى دفعات مستقلة للزر
   والعداد وصورة كل طبعة؛ الاختبارات الداخلية تظل تفصيلية دون تضخيم الإنجاز.

## التالي الآن، دون العودة لتجزئة الصور

1. صندوق التنبيهات F15، ثم رحلة الدخول والتفضيلات F16.
2. استكمال مشاركة الصور P26 كملفات فعلية، ثم قبول مسارات الاستيراد والنشر.
3. بقية الصور F07 كتذكرة مجمعة واحدة؛ لا تمنع الانتقال للوظائف الأخرى.

هذا ترتيب محلي مقترح من الفجوات المثبتة، لا إثبات وجود عطل جديد في كل بند.
أي عطل وظيفي حرج يؤكده المستخدم يسبق التجميل. لا تعاد صياغة قسم وافق عليه
المستخدم إلا لعطل موثق أو طلب صريح. فحص الجهاز والخدمات لا يغلق بالفحص المحلي.

## قاعدة العمل من الآن

- سجل واحد لكل مشكلة جذرية: **مثبتة ← جارٍ الإصلاح ← قبول محلي ← قبول جهاز/
